# 雷军 LLMWiki

累积理解雷军、小米及其经历、决策、产品、工程、管理、商业思考与演变。资料之间会相互补充、修正和连接；知识页在阅读中生长，并持续重写。

人工维护原始资料，Agent 维护 Wiki，Git 保留每次知识事务的历史。`raw/` 是证据，`wiki/` 是理解，`AGENTS.md` 是维护纪律。精确事实必须回到 raw；Wiki 本身不能充当证据。

## 最小结构

| 路径 | 职责 |
| --- | --- |
| `raw/books/` | 书籍原文；按自然章节阅读 |
| `raw/interviews/` | 访谈原文 |
| `raw/speeches/` | 演讲原文 |
| `raw/wechat/` | 公众号文章原文 |
| `wiki/index.md` | 简单的阅读地图 |
| `wiki/log.md` | 来源检查、阅读范围、语义变化和阶段验收 |
| `AGENTS.md` | 阅读、写入、证据和阶段门控规则 |

不预设知识页，不建立页面类型目录，也不增加 tags、score、confidence、keywords、canonical IDs、固定 ontology 或 YAML schema。原文中已有的格式与字段原样保留。

## 使用

Agent 开始工作先读 `AGENTS.md`、index 和近期 log。查询先沿 index 读相关 Wiki，必要时文本搜索，精确事实和来源冲突回 raw。首次 ingest 前 index 可以为空，空白不表示资料不存在。

新来源优先重写相关旧页。只在现有页面无法自然承载且值得长期讨论时新建主题页。事实段落就近链接原文，保留说话人、时间、分歧和未知。页面正文用 `[[页面名]]` 表达真实关系；GitHub 原生页面不解析这种链接，可通过 index 的普通 Markdown 链接导航。

每次事务均须完成完整阅读、相关页搜索、改写、回读核对、index/log 维护、包含未跟踪新页的完整 diff 和默认的人工 review。Agent 自查不冒充人工 review；用户明确要求不停止等待时，可以继续提交，但必须在 log 如实记录豁免。每个验收通过的步骤单独 commit，来源逐份提交，书籍逐章提交；提交不得混合结构与知识改动。具体流程见 `AGENTS.md`。

## 严格串行路线

前一阶段不过 Exit Gate，绝不进入下一阶段。不同时 ingest 与造基础设施；失败就在当前阶段修复，再验收。详细事实与实际进度由 `wiki/log.md` 记录，表格不是完成声明。

| 阶段 | 工作 | Exit Gate 与返工路径 |
| --- | --- | --- |
| P0 原则冻结 | 只写维护纪律与项目目的 | 仅读 AGENTS 即能明确回答 raw 修改权、新页条件、旧页条件、查询入口、回 raw 条件、冲突处理和 ingest 收尾七个问题；不一致则修规则 |
| P1 结构重置 | `data/raw/` 原样迁到 `raw/`，建立 index/log | 原文件内容不变；README、AGENTS、index、log 存在；Wiki 真实知识页必须为 0；失败则只修结构 |
| P2 Raw 检查 | 核对身份、重复/重叠、完整性和时间 | 列出实际来源数量、可用范围、重复关系、损坏和 unresolved；未知必须显式记录；不能把采集时间当事件时间或把错书作为证据 |
| P3 六份 Bootstrap | 高交叉、跨时间来源，严格逐份 ingest | 第 4–6 份的重要变化以旧页更新为主；至少几个页面被三份以上来源连续改写；正文有语义链接，观点有归因，index 保持简单；否则修 contract 并重跑 |
| P4 首次 Wiki Review | 暂停 ingest，审八类组织问题 | 粒度、同义主题、摘要倾向、只追加不改写、归因、链接、index 和 AGENTS 均审查；出现失败模式则修规则，重跑一至两份，再验收 |
| P5 短资料主体 | 未处理演讲 → 访谈 → 公众号；每五份轻审 | 稳定 hub、旧页更新占主导、交叉引用、自然主题群落形成；可通过 Wiki 综合回答，通过 raw 核查精确事实；失败回本批次修复 |
| P6 中期结构 Review | 停止 ingest，审 hub、范围、合并、标题、index | 人和 Agent 从 index 能理解知识空间；分组只在 index 中自然形成；仍不引入额外搜索基础设施 |
| P7 长书逐章 | 每个自然章节独立阅读、改写、review、commit | 书主要深化已有理解，没有章节摘要仓；所有处理/未处理范围清楚；受损或错配资料先隔离；结构失效则回 P4/P6 |
| P8 全局 Lint 与重构 | 先报告与人工 review，再依次合并、拆分、改名、重写、修链接、重建 index、最终核对 | 每类动作单独提交；机械链接与路径有效，语义范围清晰、来源归因和时间稳定、冲突保留；失败回对应修复动作 |
| P9 工具决策 | 已观察问题逐一对应工具 | 无痛点就不加工具；选择须说明实际故障和解决范围，不能提前建立基础设施 |

P3 的起始候选顺序为《程序人生》、2007 年采访、2020 年度演讲、2022 年创业思考访谈、造车深度专访、2025 年度演讲。必须先通过 P2 检查；身份与时间以内容证据为准，不能照文件名猜。

P5 每批只观察新建与改写页、异常重复、index 可读性和摘要倾向；最后不足五份也做收尾 review。旧页触及情况用于判断结构是否成熟，不存成评分或 KPI，也不为提高比例制造无效修改。

P7 的存储单位是整书，阅读与提交单位是自然章节、序言或前言。不能用固定 token chunk 替代章节，不能用一个整书 commit 掩盖结论演化。实际可用书目以 P2 身份核查为准。

任何阶段，只要“新资料正在改进已有理解”没有增强，就暂停 ingest，修维护规则与 Wiki 结构。知识页数量增长不能替代这一判断。

## 工具边界

只有 P8 通过后才作 P9 决策：反复出现断链才考虑 link checker，改名反复漏入链才考虑 rename helper，index 超出可用规模才评估词法搜索，中文文本召回不足才评估 BM25/qmd，没有文件系统访问的 Agent 确有需求才考虑 MCP，实际并发写冲突才考虑协调，人需要图形浏览才采用现成 UI。

向量数据库、图数据库、confidence/quality score、decay、memory tier、typed entity 默认不引入。阶段检查可以在工作区做一次性核对，不将临时审计脚本变成仓库基础设施。
